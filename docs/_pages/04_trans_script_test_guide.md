# 1. Overview
## 1.1. Target Services and Purpose of This Document
This document guides how to test whether the script is installed correctly when installing the new script (trans version) on a site in order to use NAVER Search Ad (SA) Premium Log Analysis or NAVER Performance Display Ad (GFA) conversion tracking services.

## 1.2. Precautions When Installing and Testing

> ##### WARNING
> When testing script installation, make sure you understand the duplicate-conversion filtering logic below before testing.
When a conversion generated by the new script (trans) occurs, old-script (cnv) conversions treated as the same conversion type are permanently filtered. Please be careful when installation testing and make sure you understand the details below.
{: .block-warning }

The NAVER ad platforms (Search Ad and Performance Display Ad) currently apply duplicate-conversion filtering logic to prevent duplicate conversion values from being counted in ad reports due to duplicate conversion logs.

The duplicate-conversion filtering logic is as follows.<br>
 . If a conversion generated by the new script occurs for a conversion type treated as the same type for a specific site identifier (NAVER common key, na_account_id), conversions generated by the old script (cnv) for that type are permanently filtered.

For example<br>
 . A site with NAVER common key `s_123` was using conversion type `No. 3` add to cart in the old script (cnv) version.<br>
 . If an `add_to_cart` log, which is the add-to-cart conversion in the new script (trans) version, occurs even once on that site, then from that point onward, conversion type `No. 3` add to cart from the old script (cnv) version is permanently filtered. (Please note that there is no way to restore old-script (cnv) version logs so they are reflected in reports again.)<br>

The conversion type numbers in the old script (cnv) version and the conversion types in the new script (trans) version are mapped as follows.

![04_tsg_01_02-01-01]({{"/assets/img/04_tsg_01_02-01-01.png"| relative_url}})

As in the add-to-cart example above, if a `lead` conversion occurs in the new script (trans) version, conversion `No. 4` in the old script (cnv) version is permanently filtered.

If you are testing installation of the new script (trans), old-script (cnv) conversions may be filtered when the filtering logic above applies.<br>
 . Therefore, when entering the conversion type string for the new script (trans) version (for example, the `OOOOOO` part of `_conv.type = "OOOOOO";`), we recommend adding `test_` in front of the conversion type string you want to use (for example, if you are testing `add_to_cart`, set it to `test_add_to_cart`). This can prevent the unwanted situation where, while testing `add_to_cart`, existing conversion No. 3 (add to cart) generated by the old script (cnv) is permanently filtered.<br>
 . We recommend entering the original conversion type string from the specification only after you have finished testing and confirmed that there are no issues.
 
※ Note<br>
  . When testing with the new script (trans) version, you can use a string other than `purchase`, `sign_up`, `add_to_cart`, `lead`, and `custom001`, which have mappings between the old script (cnv) version and the new script (trans) version, when entering the conversion type string (for example, the `OOOOOO` part of `_conv.type = "OOOOOO";`).<br>
 . You can also test with a string that does not exist in the official documentation (for example, `test_add_to_cart`). <br>
 . However, to prevent possible mistakes and for convenience, we recommend using the format `test_OOOOOO` in front of the conversion type string you want to use.<br>
 

# 2. Test Method
## 2.1. Preparations Before Testing
 (1) Complete insertion of the set of scripts for ad conversion tracking on the site you want to test. (You may also insert the script only on the specific page you want to test and proceed with testing.)<br>
 (2) Prepare a tool that can monitor HTTP on the device you will use for testing (for example, a desktop PC).<br>
 (3) Prepare a JSON parser tool/web service that displays JSON clearly. <br>

※ [Reference 1] HTTP monitoring tool<br>
 . Prepare an HTTP monitoring tool that shows every log sent from the device to the log collection server. (Chrome DevTools only shows HTTP generated in that browser window, so it may not be suitable as a monitoring tool. This document explains a testing method using a tool called Fiddler Classic.)<br>
  . You can download Fiddler Classic from https://www.telerik.com/fiddler/fiddler-classic.<br>

※ [Reference 2] JSON parser<br>
 . The information sent to the collection server is in plain-text JSON format, so it is not very readable when viewed directly. Using a JSON parser makes it easier to check the information.<br>
 . When preparing a JSON parsing tool/web service, you need one that can also display double JSON (nested JSON).<br>
 . This document explains a testing method using https://jsongrid.com/.<br>

## 2.2. Tool Setup / How to Use
### 2.2.1. HTTP Monitoring Tool Fiddler Classic Setup / How to Use

You can make testing more convenient by configuring the HTTP monitoring tool Fiddler Classic as follows.

■ How to configure Fiddler Classic<br>
 . Run Fiddler Classic.<br>
 . Make sure `Capturing` is displayed in the lower left. (If it is not displayed, click that area with the mouse to change it.)<br>
 . Select the Filters tab on the right.<br>
 . Click UserFilters to check it.<br>
 . In the combo box under Hosts, select `-No Zone Filter - ` and `Show only the following Hosts`.<br>
 . Enter `wcs.naver.com` in the text area. (`wcs.naver.com` is the log collection server.)<br>
 . Moving to another tab saves the setting.<br>
With the above settings, among the various HTTP requests generated during testing, only logs sent to `wcs.naver.com`, the ad-conversion log collection server, are shown in the tool, making testing easier.<br>

■ How to check logs in Fiddler Classic

When a log occurs, click (host) wcs.naver.com in the HTTP list on the left, select `Inspectors` among the tabs on the right, and select `Raw` among the lower tabs.<br>
The section starting with `{"wa":...` near the bottom of the light-blue panel through the end is the `information` portion of the log generated by the site.<br>
